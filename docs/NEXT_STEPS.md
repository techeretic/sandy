### Deferred product items

1. **Extra report formats (DOCX/XLSX/PDF) — issue #14 — HTML done, binaries remain.**
   - **Done (HTML first):** `renderReport(format, input)` + `renderHtmlReport` in `src/orchestrator/report.ts` — Markdown stays the source of truth, HTML is a deterministic view over the same `(claims, gaps)` (content identical, SD-06; all text HTML-escaped). `reportFormat` is wired through `Orchestrator` (default filename extension follows the format), `createOrchestrator`, `createSandy` (from `preferences.default_report_format`), and the loop's narrate re-render. `loadSandyConfig` **fails closed** on an unimplemented format (a `ConfigError`, not a silent Markdown fallback) and exposes a narrowed `LoadedConfig.reportFormat`.
   - **Remaining (higher effort):** DOCX/XLSX/PDF renderers. Each is another view over the same structured `(claims, gaps)` — no new logic, just a new transform. Add each to `REPORT_FORMATS` + the `renderReport` dispatcher as it lands; the fail-closed loader check then admits it automatically. A per-format test asserting the same claims/provenance survive the transform is required (the HTML suite in `tests/orchestrator.test.ts` is the template).
   - **Keep:** fail-closed (an unimplemented format is a config error, not a silent Markdown fallback); provenance/claims identical across formats (SD-06 — the *content* must not change, only the presentation).

2. **Recurring report templates (RG-08) — issue #15 — done (on-demand v1).**
   - **Done:** a template is exactly an `orchestratorRequestSchema` object (the same shape `sandy run <request.json>` and `POST /run` take). `src/orchestrator/templates.ts` holds the registry schema + fail-closed `loadTemplateRegistry`, the shared `legalToolCatalog` + `validateRequest` (the schema + legal tool catalog check the CLI, the API, and the loop's plan validation all now use — nothing new is legal because a request is "saved"), `resolveTemplate`, and `parseRunBody`. The registry is an optional `templates: { "path": "./templates.json" }` in `sandy.json` (example in `config/templates.json`), loaded and cross-checked against the manifest at config load (unknown server / non-allowed tool → `ConfigError`, fail-closed). `sandy run <template-name>` (an existing file always wins as a request file; an unknown name is a usage error) and `POST /run { "template": "<name>" }` (no registry → 400) both resolve to the unchanged `sandy.run`; a template run is audited (`template_run`) and the job carries its `template`.
   - **Remaining (v2, out of scope here):** "on a schedule" re-run — the supervisor's job (systemd/launchd/timer launching `sandy run <template>`; design §6), plus any template management UX.
   - **Keep:** a template is validated by the *same* `orchestratorRequestSchema` + legal tool catalog as an ad-hoc request (nothing new is legal because it's "saved"); fail-closed everywhere (bad registry, unknown template, illegal tool → refused, never a silent guess).

3. **Write-back (Q6 — the biggest, most design-heavy) — issue #16 — v1 core done (approval-gated write path).**
   - **Done (core):** the gate contract got its non-default implementation. (a) **Admin write allowlist** — optional `write_allowlist` in `sandy.json` (issue #16 / Q6), cross-checked against the manifest fail-closed at config load: an entry naming an unknown server or a tool outside the server's `allowed_tools` is a `ConfigError`, so the write allowlist is always a *subset* of the read allowlist (CP-02: policy > preferences; the read allowlist is untouched). (b) **`PolicyApprovalGate`** (`src/orchestrator/write-gate.ts`) — a `WriteApprovalGate` that allows a write only when the target is on the allowlist AND an explicit `WriteApproval` (task-bound, single-use, named approver + reason) is presented; it is consumed on use and can never be replayed (no standing blanket consent). `createSandy` builds a `PolicyApprovalGate` when `write_allowlist` is configured, else the default **`ReadOnlyGate` (refuse all writes — fail closed)**. `Orchestrator.write(tasks, approvals)` routes an approved write to the server (still through the MCP tool allowlist + NetworkGuard), audits **every** attempt + decision (`write_attempt`, incl. the approver), surfaces progress events, and treats a refusal as terminal (never retried, never a claim/gap). The approval surface is the **`sandy.write`** plugin tool (`sandy.status` now reports the write posture) — the in-band `needsConfirmation` precedent, extended to an audited approval. `sandy.check` shows `write: { enabled, allowlist }`.
   - **Remaining (v2, the "UX is the surface" half):** richer approval UX (a first-class approval prompt/consent flow in a host UI, approval expiry/revocation, per-arg constraints on allowlisted tools) and any durable approval audit store. The gate + allowlist + single-use approval core is what this issue asked for.
   - **Keep:** never auto-confirm (FM-04 precedent); a write is a distinct audited event; the read allowlist is untouched; default = `ReadOnlyGate` (refuse all writes).

## Conventions to keep
- **Fail closed** everywhere; never smooth over a gap; policy > preferences (tighten-never-loosen).
- Secrets only as `${ENV_REF}`; resolve at point of use, never store/log; args logged by hash only (AU-02).
- No network outside the declared MCP allowlist — everything goes through `NetworkGuard`.
- TypeScript strict, ESM, Node ≥ 22. **Pin `typescript@5.9`** (7.x native compiler has a `@types/node` auto-include bug — see DIARY 2026-08-17 afternoon).
- Run `npm run typecheck && npm test` after changes; `npm run build` for dist.
- Update `docs/DIARY.md` per work block; keep `README.md`'s Status section current. **Doc roles (per issue #13):** DIARY = chronological history (append-only), NEXT_STEPS = forward-looking state + this roadmap, README = short headline status + links. Don't restate a milestone in more than one of them.
