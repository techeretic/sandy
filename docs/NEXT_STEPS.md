## Status

**v0.3.0 (2026-09-26). Hardening from a real-world field test.** Sandy v0.2.1 was run end-to-end against a public third-party MCP server (`@cyanheads/libofcongress-mcp-server@0.3.0`) under macOS Seatbelt and then under a read-only Docker container on Linux (`blog/library-of-congress.md`); every finding was fixed (PRs #51–#58, #60). The notable ones: a **security fix** — on a Linux host running Docker, the container detector matched other containers' overlay mounts in `/proc/self/mountinfo`, so the bare host was detected as `docker` and a `runtime: "docker"` config started unsandboxed (fail-open); only the process's own root mount is inspected now. `sandy import` converts **MCP Registry `server.json`** deterministically (`src/import-registry.ts`; `--tools` required, `--registry-source` when both a remote and a package are offered), `--apply` bootstraps the first server and rolls back a refused apply byte-for-byte, and a failed fetch is audited. `macos-sandbox-exec` is detected by a nested no-op probe. Reports are never silently dropped (`run`: a filename/format mismatch is exit 2 before any MCP call; `run`/`ask`: an unwritten report — incl. a failed multi-round consolidation — is `report: NOT WRITTEN`, exit 1; a model-proposed filename the format can't use is dropped; a failed narrate re-write degrades instead of crashing). Markdown footnotes pair. stdio MCP servers' stderr is drained (an unread pipe could block a non-Node server) and a startup failure carries its stderr tail. Audit events carry a per-invocation `session` id. The `custom` DEGRADED message is accurate. See `docs/DIARY.md` 2026-09-24 and 2026-09-26. On top of **v0.2.0 (2026-09-22)** — the first feature release beyond the 0.1.x line, which added **`sandy import`** — URL- and file-driven MCP server configuration (PRs #47/#48): point Sandy at a URL, a file, or stdin that describes an MCP server and it produces a validated, content-hash-pinned, reviewable candidate config. This is the first change to the egress surface: the import dial is the **one bounded, human-confirmed, audited exception** to "zero egress outside declared endpoints" (see the threat-model note in `guide/security.md`). Everything from v0.1.3 is unchanged and still holds.

- **387/387 tests** (was 349 at v0.2.1), typecheck + build green, conformance (in-process + the Docker/Firejail `boundary × mode` matrix) green.
- **`sandy import <url|file|->`**: one-shot confirmed fetch (30s / 1MB / 3-redirect caps) → validated against the *existing* `mcpServersManifestSchema` (fail-closed, exit 3 — the schema is the law, nothing is legal because a URL said so) → staged under `.sandy-import/<sha256>.json` (content-hash pinned: a changed URL is a *new* hash, a fresh reviewable diff, never a silent mutation) → explicit `--apply` only (merge preserving existing entries, refuse name collisions, re-run the full config load as the final gate). The review package prints the exact `sandbox.allowed_network` lines to add, the env-var **names** to export (never values), and the per-server allowlist — which is **never auto-expanded** (confirm it or pass `--tools`, validated against capabilities). Audit events: `import_fetch` (url, outcome; on success finalUrl, sha256, bytes; on failure the error — a failed dial is audited too) + `import_staged` (path, hash, servers, applied). v1 is **deterministic-only**: prose is rejected fail-closed; the LLM-transcription `--auto` path is a documented follow-up (the core has no LLM client in v1). Air-gap works via file/stdin with zero network. Design: `docs/IMPORT_DESIGN.md`; plan: `docs/PLAN_IMPORT.md`.

### Deferred product items

1. **Extra report formats — issue #14 — DONE (all five: Markdown, HTML, DOCX, XLSX, PDF).**
   - **Done (HTML, v0.1.2):** `renderReport(format, input)` + `renderHtmlReport` in `src/orchestrator/report.ts` — Markdown stays the source of truth, HTML is a deterministic view over the same `(claims, gaps)` (content identical, SD-06; all text HTML-escaped).
   - **Done (DOCX/XLSX/PDF, v0.1.3):** the three **binary** formats, each a deterministic view over the same `(claims, gaps)` (SD-06 — content identical across all five; only the presentation differs). They are **byte artifacts, not text**, so the string-based report pipeline gained a binary seam: `renderReportArtifact(format, input): Buffer` (all five) alongside the text-only `renderReport`; `OrchestratorResult`/`LoopResult`/`ReportToolResult` carry the artifact as `reportArtifactB64` (base64) in-band; the File Manager gained a byte-exact `writeBinary` (magic-prefix validated: ZIP `PK` for docx/xlsx, `%PDF-` for pdf; journaled as base64 so undo is byte-exact). The containers are **hand-rolled, zero-dependency** (the repo keeps the npm install clean): `src/orchestrator/zip.ts` (deterministic STORE ZIP — fixed timestamps + part order, so identical input → byte-identical archive), `docx.ts` (WordprocessingML), `xlsx.ts` (SpreadsheetML, one worksheet per section, title carried), `pdf.ts` (PDF 1.4, A4, base-14 Helvetica/WinAnsi, word-wrapped paginated flow, correct xref). Wired through the orchestrator's `writeBinaryReport`, `createOrchestrator`, the loop's multi-round **consolidation** + **narrate** re-renders, and the plugin's `sandy.report`. `REPORT_FORMATS` now lists all five, so the loader admits them; the format check stays fail-closed as defense in depth (schema vs `REPORT_FORMATS` divergence → `ConfigError`, never a silent Markdown fallback).
   - **Keep:** fail-closed (a corrupt/binary-named text write is refused, an unimplementable format is a config error); provenance/claims identical across formats (SD-06); zero new runtime dependencies.

2. **Recurring report templates (RG-08) — issue #15 — done (on-demand v1).**
   - **Done:** a template is exactly an `orchestratorRequestSchema` object (the same shape `sandy run <request.json>` and `POST /run` take). `src/orchestrator/templates.ts` holds the registry schema + fail-closed `loadTemplateRegistry`, the shared `legalToolCatalog` + `validateRequest` (the schema + legal tool catalog check the CLI, the API, and the loop's plan validation all now use — nothing new is legal because a request is "saved"), `resolveTemplate`, and `parseRunBody`. The registry is an optional `templates: { "path": "./templates.json" }` in `sandy.json` (example in `config/templates.json`), loaded and cross-checked against the manifest at config load (unknown server / non-allowed tool → `ConfigError`, fail-closed). `sandy run <template-name>` (an existing file always wins as a request file; an unknown name is a usage error) and `POST /run { "template": "<name>" }` (no registry → 400) both resolve to the unchanged `sandy.run`; a template run is audited (`template_run`) and the job carries its `template`.
   - **Remaining (v2, out of scope here):** "on a schedule" re-run — the supervisor's job (systemd/launchd/timer launching `sandy run <template>`; design §6), plus any template management UX.
   - **Keep:** a template is validated by the *same* `orchestratorRequestSchema` + legal tool catalog as an ad-hoc request (nothing new is legal because it's "saved"); fail-closed everywhere (bad registry, unknown template, illegal tool → refused, never a silent guess).

3. **Write-back (Q6 — the biggest, most design-heavy) — issue #16 — done (core + approval-UX v2 half).**
    - **Done (core, v1):** the gate contract got its non-default implementation. (a) **Admin write allowlist** — optional `write_allowlist` in `sandy.json` (issue #16 / Q6), cross-checked against the manifest fail-closed at config load: an entry naming an unknown server or a tool outside the server's `allowed_tools` is a `ConfigError`, so the write allowlist is always a *subset* of the read allowlist (CP-02: policy > preferences; the read allowlist is untouched). (b) **`PolicyApprovalGate`** (`src/orchestrator/write-gate.ts`) — a `WriteApprovalGate` that allows a write only when the target is on the allowlist AND an explicit `WriteApproval` (task-bound, single-use, named approver + reason) is presented; it is consumed on use and can never be replayed (no standing blanket consent). `createSandy` builds a `PolicyApprovalGate` when `write_allowlist` is configured, else the default **`ReadOnlyGate` (refuse all writes — fail closed)**. `Orchestrator.write(tasks, approvals)` routes an approved write to the server (still through the MCP tool allowlist + NetworkGuard), audits **every** attempt + decision (`write_attempt`, incl. the approver), surfaces progress events, and treats a refusal as terminal (never retried, never a claim/gap). `sandy.check` shows `write: { enabled, allowlist, approvalTtlSeconds }`.
    - **Done (v2, the "UX is the surface" half):** (a) **Per-arg constraints** — a `write_allowlist` entry may carry `args`, a JSON Schema fragment the write's args must satisfy (checked with ajv in the gate, the same library the MCP SDK uses for `structuredContent`): every stated constraint must hold and args may carry further keys; a constrained key must be present; a *malformed* constraint fails closed (`args-not-allowed`), never a silent no-op. (b) **Expiry + revocation** — approvals are time-bound by construction: `policy.approval_ttl_seconds` (default 1800, capped at a day) is the default window; an approval's explicit `expiresAt` may only shorten it; `PolicyApprovalGate.revoke()` withdraws consent before use (a revoked pair can never approve again); new audited refusal reasons `approval-expired` / `approval-revoked` (distinct from `no-approval`). (c) **Consent flow** — the plugin's **`sandy.write.approve`** (record the user's consent; the receipt carries the computed `expiresAt`) and **`sandy.write.revoke`** (withdraw it) tools; `decide()` resolves a task's pending approval, so inline `approvals` and recorded consent are symmetric; `sandy.write`'s result surfaces **`needsApproval`** (the `needsConfirmation` precedent for writes) listing the legal-but-unapproved tasks — a policy refusal is never listed (asking can't make it legal).
    - **Remaining (v3, if ever wanted):** a durable approval audit store (the in-session JSONL audit already records every `write_attempt` + decision) and any host-UI-specific consent rendering — both out of scope here.
    - **Keep:** never auto-confirm (FM-04 precedent); a write is a distinct audited event; the read allowlist is untouched; default = `ReadOnlyGate` (refuse all writes).

4. **URL-driven MCP server configuration — `sandy import` — DONE (deterministic v1, v0.2.0).**
   - **Done:** `sandy import <url|file|->` (PRs #47/#48, `docs/IMPORT_DESIGN.md` + `docs/PLAN_IMPORT.md`). The pipeline is **fetch → sniff → validate → stage → (apply)** with a single trust gate: the fetched/read content runs through the *existing* `mcpServersManifestSchema` (fail-closed, exit 3), so nothing is legal because a URL or a model said so. The fetch is the **one bounded, human-confirmed, audited exception** to zero-egress (`import_fetch` event, 30s / 1MB / 3-redirect caps, non-http(s) refused). Staging is **content-hash-pinned** under `.sandy-import/<sha256>.json` — a changed URL is a *new* hash, so a remote update is a fresh reviewable diff, never a silent mutation (the VCS-reviewed-registry model holds). Only `--apply` touches live config, and it re-runs the full `loadSandyConfig` as the final gate (VPN-02 / env refs / schema) and refuses to overwrite an existing server name. The review package prints the exact `sandbox.allowed_network` lines to add, the env-var **names** (never values), and the per-server allowlist — which is **never auto-expanded** (confirm it or pass `--tools`, each tool validated against the server's capabilities). The file/stdin path needs no network, so an air-gapped box can import a manifest fetched elsewhere. Test seams: `fetcher` / `confirm` / `now` (the fetcher seam proves no dial happens before confirmation).
   - **Remaining (v2, out of scope here):** the **`--auto`** LLM-transcription path for prose URLs (and `--auto-model` for the standalone tier). v1 is deterministic-only and rejects prose fail-closed. A clean home needs an LLM client in the core (plugin mode reasons in the host; the standalone model engine lives inside the sandbox loop) — so this is likely a `sandy ask`-adjacent or dedicated engine call, not a fetch-path add-on. The design's "Open questions" (third-party "server card" registry formats; which remote endpoints `--auto-model` may use under egress policy; pre-validating a `stdio` command in-sandbox at apply time) are all deferred with it.
   - **Keep:** the fetch is not the trust (the schema is); the import dial is confirmed + audited + bounded, never a general fetcher; the imported endpoint still needs a reviewed `allowed_network` entry; the read allowlist is the operator's, confirmed at staging.
