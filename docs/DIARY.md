### Egress conformance test (NEXT_STEPS item 3) — launch success criterion

Proved "zero network egress outside declared MCP endpoints" (SB-09 / PRD §11-12) two ways: **in-process** (always runs in CI) and **at the network level in Docker** (the strongest claim, first-class and CI-runnable).

- **`src/mcp/transports.ts` — made egress blocks auditable.** `guardedFetch` now takes an optional `AuditLogger` and, when it refuses a dial, records an `egress_blocked` event (AU-01). The event type existed but was never wired — a block is now a fact in the audit trail, not a silent throw.
- **`conformance/ep-server.mjs`** — a real **streamable-HTTP** MCP endpoint (exposes `read_deals`) that listens on a port. Optional `EP_LOG` env makes it append every request it receives — that file is the network-level "egress is observable" signal (the declared endpoint is hit, and it says so). Stateless streamable-HTTP needs a fresh `McpServer`+transport per request (the SDK binds one protocol to one connection) — that was the one non-obvious gotcha.
- **`conformance/egress.test.ts`** (5 tests, in-process, always runs):
  1. a real run against the live HTTP endpoint — **every URL dialed is the declared endpoint** (recording fetch under `guardedFetch`);
  2. an undeclared endpoint is refused and **the dial never happens** (VPN-02);
  3. an egress block is **recorded as `egress_blocked`** in the audit log (AU-01);
  4. a full `createSandy` run routes **all** egress through the guard to the one declared endpoint;
  5. the loader **fails closed** on a remote endpoint not in `allowed_network` (VPN-02, config-time).
- **`conformance/Dockerfile`** + **`conformance/run-docker.sh`** (network-level, Docker). The sandbox boundary is a Docker **`--internal` network** — the runtime guarantees a container on it has *zero* external egress; it can only reach other containers on that network. So the declared MCP endpoint = an EP container on the network; the internet / other hosts = unreachable by boundary. Asserts:
  1. `sandy run` **succeeds** against the single declared endpoint (provenance claim + confined report) and the EP logs that it was actually hit;
  2. an independent **external-egress probe from inside the sandbox FAILS** (explicit, verifiable: the boundary blocks non-declared egress);
  3. the reverse — a config with an endpoint **not in `allowed_network` fails closed** at startup (VPN-02) and the EP is **never reached**.
- **Scripts:** `npm run test:conformance` (in-process), `npm run conformance:docker` (build + Docker), `npm run conformance` (both).
- **Verified:** in-process 5/5; Docker harness PASSES all three (run succeeded + EP hit, external egress BLOCKED, VPN-02 fail-closed with nothing leaving), clean teardown.
- **Note:** SB-09 wants ≥2 sandboxes. Docker is done here. **Firejail is the same harness with the boundary command swapped** (the enforcer is runtime-agnostic) — left as item 4, since firejail isn't installed in this environment to verify against.

### Sandbox conformance matrix (NEXT_STEPS item 4) — SB-09/10, runtime-agnosticity proof

Proved the enforcer is runtime-agnostic (SB-10): the SAME config + the SAME request, run under a Docker container AND a Firejail jail (both with no external egress), produce **byte-identical behavior**. This also surfaced and fixed a real detection bug.

- **Bug found & fixed in `src/sandbox/detect.ts` (`inFirejail`).** Real firejail (0.9.72, verified by installing it) sets `container=firejail` in the environment — it does NOT set `FIREJAIL=1` and does NOT create `/.firejail` in all builds. The detector only checked the latter two, so a firejail jail was never detected; on a Docker *host* the inherited cgroup/mountinfo then made it report `docker`, and a config declaring `firejail` was refused fail-closed with a runtime-mismatch (exit 4). Fixed by adding `ctx.env["container"] === "firejail"` and documenting why firejail is checked before docker (a firejail jail on a docker host must report firejail). Added 4 tests to `tests/sandbox.test.ts`, including the nested "firejail wins over inherited docker signals" case (the CI Docker-in-Docker scenario).
- **`conformance/stdio-server.mjs`** — a stdio MCP endpoint (mirrors the test fixture). stdio, not HTTP, so the fixture needs no network and the matrix isolates *boundary* behavior (detection / capability report / confinement / provenance) from egress (which `run-docker.sh` covers).
- **`conformance/signature.mjs`** — projects `sandy check`/`run` JSON onto the **runtime-agnostic behavior signature**: the capability decision (`ok`/`degraded`/`lost`/`summary`), the egress allowlist, the MCP fleet outcome (connected/failed), and the provenance (each claim's text/server/tool/`argsHash` + each gap's reason). It deliberately **drops** the fields that are legitimately runtime-specific (the detected runtime name + evidence, absolute workspace paths, wall-clock timestamps, durations, the full audit transcript) — so "identical behavior" is asserted where it means something, not on a naive byte diff that can never be stable.
- **`conformance/sandbox-matrix.sh`** — runs the same `check`+`run` under both boundaries and asserts: (1) each boundary reports `ok:true`, non-degraded, the `crm` server connected, a claim returned, and a report written to the confined dir; (2) **the two boundaries produce byte-identical signatures**. Modes: `SANDY_MATRIX=docker|firejail` (one leg, for CI) or unset (both + the cross-boundary diff). `SANDY_REQUIRE=1` fails closed when a boundary is missing (CI uses it); otherwise a missing boundary is reported and skipped so the suite stays green on hosts without it. ### Phase 2 design review + revision — 2026-08-20

Reviewed the Phase 2 draft **against the actual code** (not just the doc) and revised it. Two of the original review concerns were based on a **false premise**, which I disproved by running the sandbox boundary directly; the rest were real gaps. Net: the architecture is sound, and the plan is now internally consistent.

- **Verified fact (corrects a review item).** A review pass initially flagged that a loopback model would be *incompatible* with the no-egress boundary. **False.** Ran a loopback vs. external probe inside every boundary the conformance uses: `docker --network none`, `docker --internal`, and `firejail --net=none` all give `loopback=OK external=BLOCKED(ENETUNREACH)`. So `llama-server` on `127.0.0.1` runs **in-sandbox** and is zero-egress by construction — the hardest architectural question (model placement) is resolved *in the plan's favor*.
- **Engine lifecycle (real gap).** The draft's "stop `llama-server` on close" had no backing: `LlmEngine` (`src/engine.ts:63`) is only `record`/`invoke`, and `Sandy.close()` (`src/sandy.ts:253`) closes only MCP + audit. Added a `start`/`isReady`/`close` contract to `LlmEngine` and wired it into `Sandy.close()` + service shutdown, so a model process is never orphaned (same class of leak already fixed for a failed MCP connect).
- **`ModelRequest` is too thin for the parse step (real gap).** It's a bare `{ prompt, maxTokens? }` — no structured/JSON-output option, which the parse step needs to reliably get `{gather, report}` from a weak 4–8B model. Flagged as an open decision (extend `ModelRequest` with `responseFormat`/schema) to settle in the same step as the lifecycle.
- **Parse robustness (real gap).** "Validate and retry" could loop unboundedly. Now: bounded retry (cap ~3) with the error fed back, then a **deterministic conservative fallback** (single obvious task or refuse-and-report) — never unbounded, never an unvalidated plan.
- **Engine start timing (real gap).** `createSandy` builds the engine object at startup (`src/sandy.ts:178`); starting a 4–8B model there would make `sandy check` expensive. Decision: construct the object eagerly (cheap), but `engine.start()` is **lazy** — on first `invoke()` and on `sandy serve` — not on `createSandy`/`check`.
- **Resource limits are unenforced (real gap).** `sandbox.max_memory_mb`/`max_cpu_percent` are declared in the schema but **nothing in `src/` reads/enforces them** — and a model is exactly what would blow a cap. The design no longer assumes the sandbox bounds the model: caps map to llama.cpp knobs; the hard ceiling is the service manager's cgroup (an in-service hard bound is a small, flagged addition if wanted).
- **Conformance "reuse unchanged" overstated (real gap).** Both harnesses hardcode `"mode":"plugin","llm":{"provider":"host"}` (`conformance/sandbox-matrix.sh:94`, `conformance/run-docker.sh:99`). Reuse requires **parameterizing the config templates** (mode + `llm`), not changing assertions.
- **API job store is unbounded (real gap).** `POST /run`→`202` needs a job registry the synchronous orchestrator lacks; in a long-lived process that's a slow leak. Now bounded (max in-flight + retention eviction; evicted id → clean `404`).
- **`SandyCheckReport` has no engine field (real gap).** "Model health is part of `check()`" needs the report to carry it — added an `engine` health field (status ready/degraded/not-started + reason).
- **Model provisioning is out-of-band (clarified).** Getting the GGUF/`llama-server` on the machine is an install-time step, never a `NetworkGuard`'d runtime path — so it's not an egress route.
- Open decisions reduced to the genuinely undecided: model/runtime distribution, default model, resource-limit scope, exact config field names, API surface scope, structured-output mechanism. Build order in §8.

### Security — GHSA-qx23-r762-x2j9: CSRF hardening on the loopback-only local API, 2026-08-23

### Hardening — in-service hard memory bound for the bundled model (issue #18)

The §4.5 "small, flagged addition." The *default* posture is unchanged — the hard memory ceiling is the service manager's cgroup (`memory.max` / `--memory` / `MemoryMax=`). This adds the **opt-in** in-service bound the design pointed at: when the operator sets `sandbox.enforce_memory_limit: true`, the model's process group is wrapped in a cgroup v2 child with `memory.max` set to the declared `sandbox.max_memory_mb`, so the ceiling holds even when the supervisor does not enforce one. Chosen mechanism: **direct cgroup v2** (no systemd dependency, works wherever cgroups are delegated); chosen fail mode: **fail closed** (a requested ceiling that can't be applied is a degraded engine, never a silently-unbounded model — the repo's "never silently unbounded" law).

- **Recon (ground truth, not reasoning):** probed the actual environments. cgroup v2 throughout. The project's sandbox image (`node:22-trixie-slim`) mounts `/sys/fs/cgroup` **read-only** and has no delegation → the bound is impossible there (hence the flag must default off and conformance stay green). On a **systemd delegated scope** (`Delegate=yes` — the realistic `sandy serve` deployment), creating a memory-bounded child cgroup under the delegated parent **works** (verified live: child created, `memory.max` set, a real process moved in and bounded, cgroup removed after exit). A plain container whose cgroup-ns root holds processes cannot do it (kernel "no internal processes" rule) — that is the fail-closed case.
- **`src/memory-bound.ts` (new):** `wrapProcessInMemoryCgroup(pid, limitBytes, ops)` — reads the calling process's cgroup v2 path from `/proc/self/cgroup`, walks up to the **nearest ancestor with the memory controller delegated** (`cgroup.subtree_control` has `memory`), creates a `sandy-model-<pid>` child there, sets `memory.max`, and writes the pid to `cgroup.procs` (the whole process group is then bounded). Fail-closed on every unverifiable step (no v2 hierarchy, no delegated ancestor, EACCES, no pid): throws `MemoryBoundError` and removes any partially-created cgroup (no leak). `releaseMemoryCgroup()` removes it after the model exits (best-effort, residual surfaced not swallowed). All fs access behind an injectable `MemoryBoundOps` so the whole sequence is testable with no root/cgroupfs.
- **Wiring (default off, only the local engine):** `sandbox.enforce_memory_limit` (strict schema, default `false`). `createSandy` passes it + `max_memory_mb` through `createLlmEngine` → `LlamaCppEngine`, which wraps the spawned model's pid **immediately after spawn** (confined for its whole life, not just after ready). On failure it kills the child and reports `degraded`. The bound is reported in `status().memory` (→ `check().engine.memory`) and the cgroup is released in `killChild()`. The cgroup factory + ops are injectable (`engineMemoryBoundFactory` in `SandyDeps`) for tests.
- **Tests (+17, 265/265):** `tests/memory-bound.test.ts` (9 — discovery walks to the nearest delegated ancestor; success sets `memory.max`/moves the pid; fail-closed on no-delegation / cgroup-ns-root / no-v2 / attach-failure with cleanup; stale-empty-dir reclaim; invalid pid/limit; release). `tests/engine.test.ts` (4 — wrap-on-start reports the bound in `status()` + release on close; fail-closed → degraded + child killed; off-by-default → factory never called; factory passes the MiB cap through in BYTES). `tests/config.test.ts` (2 — default false, true accepted, non-boolean fails closed). `tests/sandy.test.ts` (2 — config flag → engine wired end-to-end with the cap reaching the factory in bytes; unset → no cgroup touched).

### Feature — multi-turn / agentic planning for the standalone loop (issue #19)

The last of the three optional-hardening items, and a design §10 non-goal for v2: extend the single gather→report pass in `src/standalone/loop.ts` (`run(goal)`) to plan a second (and, bounded, further) round from the first results. The issue's stated invariant is the design spine: **the validate-then-run seam (`parse` → `orchestrator.run` → `narrate`) is what this extends, and the schema-validation + legal-tool-catalog gate (`validatePlan()`) applies to EVERY round, not just the first.**

- **The loop (`src/standalone/loop.ts`):** `AutonomousLoopOptions` gained `maxPlanningRounds` (default **1** = the existing single pass, so behavior is untouched unless opted in). With >1, after each gather pass the loop calls a new `replan()` step: the model sees the goal, the rounds gathered so far (claims + gaps, truncated), and the exact calls already made, and returns `{"decision":"stop"}` or `{"decision":"gather","gather":[...]}`. Each proposed follow-up task passes the **same** `validatePlan()` gate (shared `validateRequest` = `orchestratorRequestSchema` + legal tool catalog) as round 1 — a later round can never be legal that round 1 could not have been; a bad follow-up is a recorded `standalone_replan` attempt failure, retried (error fed back, same ≤3 cap), and on exhaustion the loop ends with what it has (`stop: "exhausted"`) — a dead model is reported, never a crash, and nothing is invented.
- **No re-gathering churn:** new `callSignature(server, tool, args)` (in `orchestrator.ts`, the same canonical form as the provenance `argsHash`) de-duplicates calls. A replan that only re-proposes a call already made contributes no new tasks and ends the loop as `stop: "nothing-new"` — so a weak model that just repeats itself terminates instead of burning identical calls.
- **One ask = one report:** later rounds run without a report; all rounds' (claims, gaps) merge, claim refs are renumbered (each `orchestrator.run` numbers from 1 — without renumbering the consolidated report would carry duplicate footnotes), and the consolidated report is re-rendered into the **round-1 report path** (best-effort: a re-write failure is audited `consolidate-error` and never discards the gathered claims/gaps). The narrate then covers the whole consolidated result.
- **Schema:** new `replanDecisionSchema` (zod; `decision: "stop"|"gather"`, `gather` reuses `gatherTaskSchema` so round-1 task rules apply verbatim) + a best-effort `REPLAN_JSON_SCHEMA` structured-output knob mirroring `REQUEST_JSON_SCHEMA`.
- **Config (fail-closed, default off):** `preferences.max_planning_rounds` — `z.number().int().min(1).max(5).default(1)`; out-of-range is a `ConfigError`, never a silent widen. `createSandy` wires it into the loop.
- **Audit + progress:** a new `standalone_replan` audit event type (per-round `stage`/`outcome`: invoke, attempt-failed, accepted, gathered, stop, nothing-new, failed, max-rounds, consolidated) + transcript rendering; three new `ProgressEvent`s (`replan-started`, `replan-attempt-failed`, `replan-stopped`) rendered by all three sinks (CLI stderr, the API's in-band/SSE progress, the plugin's `ProgressCollector`). `LoopResult` gained an optional `replanning: { rounds, gatheredRounds, stop }` (surfaced in `sandy ask --json` + the CLI text output).
- **Threat model (design §2.1 note extended):** the replan prompt, like narrate, embeds untrusted `claim.text`; its blast radius is strictly bounded — the only outputs are `stop` or gather tasks that pass the round-1 gate, so the worst case is a few extra *legal* read calls within the round cap, never an unvalidated request, never a write.

### Feature — write-back approval UX v2 (issue #16 remaining half): consent flow, expiry/revocation, per-arg constraints

The last remaining deferred item (NEXT_STEPS "Suggested first action"): the "UX is the surface" half of Q6. The core gate + admin write allowlist + single-use approval already existed (issue #16 v1, 2026-08-24); this adds the three things the issue's v2 half named — **a first-class approval consent flow, approval expiry/revocation, and per-arg constraints on allowlisted tools** — keeping the fail-closed law end to end (default `ReadOnlyGate`, never auto-confirm, a write is a distinct audited event, the read allowlist untouched).

- **Per-arg constraints (CP-02, stricter than before).** `write_allowlist` entries may now carry `args` — a JSON Schema fragment that the write's args must satisfy (`src/config/schema.ts`). Semantics mirror the MCP SDK's `structuredContent` validation: **every stated constraint must hold, and args may carry further keys** (a constraint pins values; it does not enumerate the full argument set — the server's own input schema remains the final authority on argument validity). A constrained key must be PRESENT (a constraint is a promise about the value, not a permission to omit it). Checked in `PolicyApprovalGate.decide()` with **ajv** (new direct dependency, pinned `8.20.0` — the same library the MCP SDK uses for `structuredContent`), under **`strict: true`** so a *malformed* constraint (unknown keyword / invalid value) throws at compile time and the gate **fails closed** (`args-not-allowed`) — `strict: false` would silently drop unknown keywords and turn a typo'd constraint into a no-op (fail open). A new refusal reason `args-not-allowed` (a distinct, audited denial, alongside `not-allowed-by-policy`/`no-approval`/`gate-refused`) is surfaced in `WriteResult.reason` (now the shared `WriteDenialReason` type) + the `write-denied` progress event (which gained `server`/`tool` so the target is named, like `write-approved`).
- **Approval expiry + revocation (contract point 4, tightened).** Approvals are now **time-bound by construction** — there is no standing blanket consent, and the window is explicit. `policy.approval_ttl_seconds` (new, `z.number().int().min(1).max(86400).default(1800)`; capped at a day — a longer window would recreate blanket consent in all but name) is the default window measured from when an approval is registered or first presented. An approval may carry an explicit `expiresAt` (ISO-8601) that **may only shorten, never extend** the default (clamped to `min(expiresAt, now+ttl)`; an unparseable value fails closed to the default). `PolicyApprovalGate` gained `revoke(taskId, approver?)` (withdraw consent before use; a revoked `(taskId, approver)` can never approve again — re-presenting is refused `approval-revoked`, re-registering is refused) and `pendingExpiry()`. The clock is injectable (`now`) so the whole expiry path is unit-tested without sleeping. Two new refusal reasons — `approval-expired`, `approval-revoked` — are NOT folded into `no-approval`: the audit record says which bound was hit.
- **The consent flow (first-class).** `decide()` now resolves a task's **pending** approval when none is passed inline (the `sandy.write.approve` path), so both consent routes are symmetric: inline `approvals` (as before) OR a consent recorded ahead of time. A *policy* refusal (not allowlisted / args out of bounds / read-only gate) is deliberately NOT listed — asking the user could not make it legal. `SandyCheckReport.write` now carries `approvalTtlSeconds` (and the allowlist entries their `args`), so `sandy check`/`sandy.status` show the full write posture.
- **Wiring (fail-closed, default unchanged):** `createSandy` builds the gate with the policy TTL; `loadSandyConfig` carries `args` through the allowlist cross-check (the subset-of-read-allowlist guarantee is untouched — `args` only constrains, never widens). The three progress sinks (CLI stderr, standalone API in-band/SSE, plugin `ProgressCollector`) render the enriched `write-denied`. ### Feature — DOCX/XLSX/PDF report renderers (issue #14, the binary half)

The remaining half of issue #14. v0.1.2 shipped the text formats (Markdown source of truth + HTML view); `preferences.default_report_format` already declared `docx|xlsx|pdf` but the loader refused them fail-closed ("not supported yet"). This implements the three binary formats, each as a **deterministic view over the same `(claims, gaps)`** as the text renderers — the content (every claim, gap, and provenance entry) is identical across all five formats (SD-06); only the presentation differs. The decisive constraint that shaped the design: **these are binary artifacts, not text.** DOCX/XLSX are OPC ZIP containers; PDF is a byte-level page tree. None of them has a lossless UTF-8 string form, so the whole report pipeline — which was string-based end to end (`renderReport: string`, `writeReport(content: string)`, `reportContent?: string`, the File Manager's utf8 `write()`) — needed a **binary-aware seam** rather than three string renderers.

- **Zero new dependencies.** The repo's philosophy is "keep the npm install clean" (3 runtime deps; plain `node:http`, hand-written HTML). Adding a docx/xlsx/pdf library for a small fixed-structure archive would break that. So the containers are **hand-rolled**:
  - **`src/orchestrator/zip.ts` (new):** a minimal, deterministic ZIP (STORE) writer — local headers + central directory + EOCD, table-driven CRC-32, a fixed 1980-01-01 DOS timestamp and fixed part order so identical `(claims, gaps)` produce byte-identical archives (the same determinism the text renderers have).
  - **`src/orchestrator/docx.ts` (new):** WordprocessingML — `[Content_Types].xml` + `_rels/.rels` + `word/document.xml`. Headings (title/Findings/Gaps/Provenance + per-task), the clearly-labeled summary, findings with inline claim refs, explicit gaps, and a bordered provenance table. All text XML-escaped; multi-line claim text keeps its line breaks (`w:br`), never collapsed.
  - **`src/orchestrator/xlsx.ts` (new):** SpreadsheetML — one worksheet per section (Summary when present, Findings grouped by task, Gaps, Provenance), inline strings, a `columnLetter` helper, and a workbook/rels/content-types wiring. **The report title is carried here** (the first Findings row) so the content is complete.
  - **`src/orchestrator/pdf.ts` (new):** a minimal PDF 1.4 — A4 pages, base-14 Helvetica family (regular/bold/oblique) with `WinAnsiEncoding`, word-wrapped text, a paginated flow (sections flow to a new page when they don't fit; a provenance entry is never split), a page-number footer, and a correct xref table (offsets computed in latin1 byte length, object numbers collision-free: page `6+2i`, content `7+2i`). Text outside WinAnsi is substituted with `?` (a viewer-faithful fallback; the report's content is ASCII-safe in practice).
  - **`src/orchestrator/xml.ts` (new):** shared XML text escaping.
- **The binary seam (the load-bearing change):**
  - **`src/files/format.ts`:** `SUPPORTED_FORMATS` gains `docx|xlsx|pdf`; `detectFormat` maps `.docx/.xlsx/.pdf`; new `BINARY_FORMATS`/`isBinaryFormat()`/`validateBinaryContent()` — **magic-prefix validation** (ZIP `PK` for docx/xlsx, `%PDF-` for pdf) so a file stored under a binary report name whose bytes are not that format is refused fail-closed (a corrupt artifact). A *text* `write()` to a binary name is also refused (`writeBinary` is the path for those bytes).
  - **`src/files/file-manager.ts`:** new `writeBinary(candidate, Buffer, options)` — the same confinement/ignore/confirmation gates, journaling, and audit as `write()`, but byte-exact: content stored raw, journaled as base64 (the same byte-exact guarantee the prior-bytes capture already gave pre-existing binaries), and undo restores prior bytes exactly.
  - **`src/orchestrator/report.ts`:** `REPORT_FORMATS` is now all five; new `renderReportArtifact(format, input): Buffer` (the on-disk bytes, dispatched across all five) and `isBinaryReportFormat()`; the existing string `renderReport` stays text-only (markdown/html). `reportFormatExtension` maps all five.
  - **`src/orchestrator/orchestrator.ts`:** `OrchestratorResult` gains `reportArtifactB64?` (the artifact as base64 — present for every format, so a binary report carries its bytes in-band instead of a non-UTF-8 string; `reportContent` stays for text). `run()` renders binary formats via `renderReportArtifact` and writes them through a new `writeBinaryReport` option (a write failure still surfaces as `reportError` + an audited `report-write` error, and the gathered claims/gaps are never discarded — the existing invariant).
  - **`src/orchestrator/factory.ts`:** `createOrchestrator` wires `writeBinaryReport` through the real File Manager's `writeBinary` (same confinement + confirmation).
  - **`src/standalone/loop.ts`:** `LoopResult` gains `reportArtifactB64?`; the multi-round **consolidation** re-render and the **narrate** re-render both handle binary (render the artifact, `writeBinary`, carry the base64). The consolidation trigger is now "round 1 produced a report" = `reportContent !== undefined || reportArtifactB64 !== undefined` (a binary round-1 report has no string content). `createSandy` already forwards `reportFormat` to the loop, so no wiring change there.
  - **`src/plugin/tools.ts` + `api.ts`:** `ReportToolResult` gains `reportArtifactB64?`; `sandy.report` returns the artifact in-band.
  - **`src/config/loader.ts`:** all five formats are now implemented, so the "not supported yet" refusal becomes a **defense-in-depth** guard (it stays fail-closed if `REPORT_FORMATS` and the schema ever diverge); the comment is updated to say so. New symbols exported from `src/index.ts`.
- **Tests (+15, 323/323):** `tests/orchestrator.test.ts` — the per-format suite (the HTML template) extended to docx/xlsx/pdf: claims/gaps/provenance survive the transform (escaped), the dispatcher + extension + `isBinaryReportFormat` mapping, a valid-ZIP structural assert (a minimal EOCD/central-directory reader added as a test helper), and a `createOrchestrator` e2e writing all three through the real File Manager (artifact base64 round-trips to disk, magic bytes valid). `tests/files.test.ts` — `writeBinary` byte-exact write + undo-restore, magic-prefix fail-closed, non-binary-name / binary-name-text-write refusals, the overwrite confirmation gate; `detectFormat`/`isBinaryFormat`/`validateBinaryContent` unit asserts. `tests/sandy.test.ts` — the old "refuses an unimplemented format" e2e becomes "renders docx/xlsx/pdf end-to-end" (default extension, valid artifact on disk, artifact base64). `tests/loop.test.ts` — the single-pass ask in each binary format (artifact on disk + in-band, narrative re-render into the artifact) and a multi-round consolidation into ONE binary report (both rounds' data in the artifact, `consolidated` audited); `makeLoop` now forwards `reportFormat` to mirror `createSandy`. `tests/plugin.test.ts` — `sandy.report` in each binary format returns the artifact in-band. The `tests/config.test.ts` "fails closed on unimplemented" test becomes "admits every implemented format" (the narrowed `reportFormat` is each of the five).
